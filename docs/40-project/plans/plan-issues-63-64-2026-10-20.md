## P1 — #63: hide the form on success, show the confirmation alone

**Parent:** #63 · **Size:** S · **Type:** bug

### Evidence

`ContactPage.tsx:276-317`:

```
278  <div className="shell grid gap-12 lg:grid-cols-[1.35fr_.65fr] lg:gap-[70px]">
281    {reference ? ( <div ref={successRef} …> Thanks — that's with our team. </div> ) : null}
317    <form ref={formRef} noValidate onSubmit={onSubmit} className="grid gap-6">
```

The form at :317 is **not conditional**. At `lg` the grid is two columns, so on success  
the confirmation takes column 1 and the still-mounted form takes column 2 — which is exactly  
the screenshot on the issue: thank-you left, live form right.

The comment at :279-280 says *"Confirmation replaces nothing — it sits above the form, so the  
user can send a second inquiry without a navigation."* **The comment is wrong about the  
rendered layout**: `grid-cols-[1.35fr_.65fr]` puts them side by side, not stacked. The  
comment describes the author's intent, not the output.

### Scope

- In: `ContactPage.tsx` — render the form only when `!reference`; confirmation becomes the  
  sole child of the form card.
- In: keep "Send another" (`setReference(null)`, :304) as the only way back to the form.
- Out: restyling the confirmation panel; the other three marketing pages (no form to fix).
- Out: the `lg:grid-cols` two-column split for the *unsent* state — that is the design.

### Acceptance

1. After a successful submit, `document.querySelector('form')` is `null` on `/contact`.
2. The confirmation is the only content of the form card, at every breakpoint.
3. "Send another" restores an empty form and moves focus into it.
4. A rendered-output check in `tests/` asserts (1) — not a source-text grep, since the  
   conditional is what changed.

### Open question

The 2-column split also lays out the *empty* state (form on the right, nothing on the left).  
When the form is hidden, does the confirmation inherit the right-hand column, or go full width?  
**Recommendation: full width** — a confirmation alone in a 0.65fr column reads like an error  
message. Needs a call before the CSS is touched.

## P3 — #64.2: Clerk organization + role for feature permissions

**Parent:** #64 · **Size:** M · **Type:** enhancement · **Blocked on:** Clerk instance config

### Evidence

`src/admin/clerkAuth.ts:15`:

```ts
return user?.publicMetadata?.role === "admin"
```

A single flat flag on the user. There is no organization, no `orgId`, no `orgRole`, and no  
per-feature permission — every signed-in admin sees all nine pages.

`RequireAuth.tsx:44` gates the whole `/admin` shell on that one boolean, and the  
`AccessDenied` copy (`:52`) tells the operator to set `publicMetadata.role = "admin"`.

### Scope

- In: decide the model — Clerk **organization** roles (`useOrganization`, `orgRole`) vs. keeping  
  flat `publicMetadata`. The issue asks for the former.
- In: extend `hasAdminRole` into a permission check that returns *which* features are allowed.
- Out: any server-side enforcement — there is no server (see P8). A client-side role check is  
  a UI gate and must be documented as such; `clerkAuth.ts:4` already says this.

### Blocked on

Organizations must be **enabled on the Clerk instance** before any code can read `orgRole`.  
Enabling them is a Clerk-dashboard change, not a repo change.

### Acceptance

1. Role resolution reads from one function; no page reads `publicMetadata` directly.
2. A signed-in non-admin sees `AccessDenied`, not a sidebar.
3. The doc comment states plainly that this is not authorization.

## P4 — #64.3: admin-only sidebar group of external links (new tab)

**Parent:** #64 · **Size:** S · **Type:** enhancement

### Evidence

`src/admin/routes.ts` models **internal routes only** — `AdminNavItem { title, path, icon, description }`.  
`src/components/app-sidebar.tsx:96` renders every item as `<Link to={item.path}>`, and  
`ADMIN_NAV` is rendered without any visibility predicate (`:88`).

So there is currently no way to express: an external URL, a new tab, or a role-gated group.

### Scope

- In: extend `AdminNavItem` with `href?`, `external?: true`, `visibleTo?: (perms) => boolean`  
  — or an explicit `ExternalNavGroup` type, to keep internal and external items from  
  sharing a shape they do not share semantics.
- In: new group in the sidebar with Clerk dashboard / Vercel / GitHub, `target="_blank"`,  
  `rel="noopener noreferrer"`.
- Out: making the URLs configurable per environment — hard-code or read from `VITE_*`, but  
  decide and say which.


### Acceptance

1. External items render `<a target="_blank" rel="noopener noreferrer">`, not router `Link`.
2. The group is absent for a non-admin (after P3 lands; today the whole shell is already  
   admin-gated, so the predicate would be tautological — **say so in the PR rather than  
   claiming a gate that does nothing**).
3. The breadcrumb does not break on external items (`AdminLayout.tsx:44` resolves  
   `findAdminRoute(pathname)`, which must not match an external href).

## P5 — #64.4: collapse Design + Reference into Settings sub-panes

**Parent:** #64 · **Size:** M · **Type:** refactor

### Evidence

`ADMIN_NAV` today (`routes.ts:47-110`) — 4 groups, 9 pages:

| Group     | Items                                     |
| --------- | ----------------------------------------- |
| Inbox     | Inquiries                                 |
| Settings  | General, Profile, Notifications, Security |
| Design    | Design System, Assets, Components         |
| Reference | Documentation                             |

`SettingsPage` is one page with no sub-pane structure. "Move Dash Design menu and other  
non-operational UI to a Settings dashboard menu with sub-panes" means the Settings group  
absorbs Design (3) and Reference (1) → **8 sub-panes under one label**.

### Load-bearing constraint — do not skip

`src/App.tsx:43-47`: admin child routes must stay **self-closing**. `tests/policy.mjs` finds  
the `/admin` catch-all with a non-greedy match from `<Route path="/admin"` to the first  
closing tag. A child written with an explicit closing tag truncates that match and the  
"unknown /admin paths redirect" check silently inspects the wrong block — **passing while  
looking at nothing**. Any new route added here must follow the rule or the check must be  
tightened first.

### Scope

- In: regroup `ADMIN_NAV`; add sub-pane navigation inside Settings.
- In: keep every existing path (`/admin/design` etc.) or redirect the old ones — a nav  
  regroup must not 404 a bookmarked URL.
- Out: rewriting the nine pages themselves.

### Acceptance

1. Sidebar shows Inbox + Settings only; every one of the 9 pages still reachable.
2. `findAdminRoute()` still resolves every path; breadcrumb leaf still correct.
3. `tests/policy.mjs` and any nav-count assertion updated **and** still able to fail.

## P6 — #64.5: membership plans (residential / landlord / multi-family) — display + inquiry only

**Parent:** #64 · **Size:** L · **Type:** enhancement · **Blocked on:** Clerk Billing verification


### Evidence

- There is **no member or plan surface** anywhere: `src/admin/` is 9 pages, none of them  
  membership-related. `ADMIN_NAV` has no Members entry.
- `@clerk/react ^6.17.8` and `@clerk/ui ^1.40.2` are installed; **no billing component is  
  imported anywhere** (`grep -rn "PricingTable\|CheckoutButton\|usePlans" src/` → 0).
- **No Stripe dependency exists** (`package.json` has none), and the site's founding rule is  
  no cookies / no third-party trackers (`CONTRIBUTING.md`; the 2026-09-29 proposal §6.3 names  
  this as a decision the client would be reversing, not a detail).

### The collision to name

**Clerk Billing is Stripe-backed.** "Use Clerk billing … skipping the stripe setup" may not be  
possible even for read-only display: if the instance has no billing connection, there are no  
plans to read. This must be verified against the actual Clerk instance **before** the task is  
sized — otherwise the task is written against a capability that does not exist.

Second collision: the repo already prices this territory —  
`docs/40-project/proposal-backend-and-lead-handling-2026-09-29.md` Option B is *"Option A +  
product & service checkout"* at $1,500. A membership page that takes inquiries is a third  
thing (display only, no checkout). Say which of the three this is before building.

### Scope (if it survives verification)

- In: a plan catalogue for three customer segments, three tiers each — the schema is the  
  deliverable; the data source (Clerk Billing vs. a local typed constant) is the decision.
- In: selecting a plan pre-fills the inquiry form (`ContactPage` `service` / `propertyType`  
  fields, `:201-210`) so the lead arrives tagged.
- Out: checkout, payment, subscription lifecycle, Stripe activation.

### Acceptance

1. Plans render from one typed source; no price is duplicated in JSX.
2. Choosing a plan carries through to the submitted inquiry record.
3. No network call to a payment provider; no cookie set (assert it).

## P7 — #64.6: audit — backend + Clerk production readiness

**Parent:** #64 · **Size:** M · **Type:** investigation (produces a document, not a feature)

### Evidence — the headline finding

`src/lib/data/api.ts:85-97`:

```ts
async createInquiry(input: NewInquiry): Promise<Inquiry> {
  …
  backend.writeInquiries([record, ...backend.readInquiries()])
```

and `backend.ts:2` — *"localStorage-backed storage engine"*.

**A public form submission is written to the visitor's own browser and never reaches the  
business.** It is visible only in the `/admin` inbox of the browser that submitted it. This is  
already documented and priced (`proposal-backend-and-lead-handling-2026-09-29.md`, Option A,  
$1,000) — the audit should confirm it is still true and not silently re-scope it.

Second finding: the admin role check is client-side only (`clerkAuth.ts:4`: *"it is not  
server authorization"*). With no server, "admin-only" means "hidden from the UI", nothing more.

### Scope

- In: a written audit — every claim carries `file:line`; no claim without one.
- In: an explicit list of what is production-ready vs. demo-only, per subsystem  
  (data, auth, roles, form handling, captcha, theming).
- Out: implementing any of it. This task produces the document the other tasks are prioritised  
  against.

### Acceptance

1. Each finding has a file:line and a severity.
2. The localStorage finding is stated in one sentence a non-engineer can act on.
3. Anything already priced in the 2026-09-29 proposal is cross-referenced, not re-priced.
