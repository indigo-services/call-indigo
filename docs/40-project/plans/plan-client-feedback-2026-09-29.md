## 3. Design decisions

Each decision names the alternative rejected and why.

### 3.1 The licence is a **code**, not a sentence — so the fix is `RMP45574 EC23851`

The client asks for `License: RMP45574 EC23851`. Rendered, that is one
concatenated token: `RMP45574 EC23851`. It looks like a typo for `RMP 45574` and
**it is not**, for one reason that is checkable rather than aesthetic:

> **Texas issues two licence numbers for the same individual — an RMP
> (Master Plumber) and an EC (Electrical Contractor) — and they are written
> without a space between the prefix and the digits. `RMP45574 EC23851` is the
> conventional form; `RMP 45574` is this site's own invention.**

The client supplied the **exact string to render**, in quotes, and asked for it in
**every instance**. **Decision: render the brief's string verbatim.** Do not add
the space back, and do not add a separator between the two codes.

**Alternative rejected:** render `License: RMP 45574 · EC 23851` (spaced, spaced
apart) on the grounds that the spacing was the original intent. Rejected — it
improves the typography of a string the client quoted exactly, and this repo has
been burned by improving a quoted string before (round 3, item 6: the carousel was
built to the letter and reverted).

⚠️ **One consequence to carry into the task, not to decide here.** The brief's
`RMP45574 EC23851` contains **no space whatsoever**. A reader who has never seen a
Texas licence will read `RMP45574` as a typo. If the client wants it to read as
two codes, `RMP45574 · EC23851` is the one-character fix — **ask before shipping,
do not pre-empt**. See §9 Q1.

### 3.2 "Emm dash" in the hero is a **CSS `::before` rectangle**, not a text character

This is the single most valuable finding in the round, and it is why the item is
its own task rather than a copy edit.

> **There is no em dash in the hero paragraph. The dash is a `::before` pseudo-
> element with no text content at all.**

```
src/index.css:1021   .banner-lead::before {
src/index.css:1022     content: "";
src/index.css:1023     position: absolute; left: 0; top: 12px;
src/index.css:1026     width: 36px; height: 3px;
```

It is a **36×3px white rectangle** (20px at ≤1440), drawn as a block-level
decoration to the left of the lead paragraph. Grepping the paragraph text for a
dash character returns the em dash in *"heater failures—our experts"* — **a
different dash, inside the sentence**, which the client did not mention:

```
src/marketing/pages/HomePage.tsx:271
  <p class="banner-lead …">Fast, licensed, and local. From leaks to clogs to <br>heater failures—our experts fix it today.</p>
```

**Decision: hide the `::before` rectangle; leave the sentence's own `—` alone.**

The paragraph's `padding-left` exists **only** to clear the rectangle
(`54px` base, `30px` at ≤1440, `27px` at ≤1199, `0` at ≤991). Hiding the rectangle
without dropping the padding leaves a **54px hole** where a dash used to be, so
the two must change together:

```css
.banner-lead::before { display: none; }
.banner-lead         { padding-left: 0; }
```

**Alternatives rejected:**

- *Delete the sentence's `—` too.* The client said *"the Emm dash in the hero"*,
  singular. There is exactly one thing on this page a reader would call an em dash
  in the hero, and it is the rectangle. Deleting the sentence dash as well changes
  copy the client **quoted approvingly** in the same sentence (*"to read 'Fast,
  licensed local…'"* — no dash in the quote). Not authorised.
- *Leave the padding.* Produces a 54px indent with nothing to indent from. It reads
  as a layout bug and would be reported as one.

⚠️ **This is the item most likely to be got wrong**, because the *string* the
client named does not exist. A task that greps for `—` in the hero finds the
sentence dash, edits it, and reports success — changing the wrong thing while
every check passes. The task text names the CSS selector explicitly for this
reason.

### 3.3 "Remove the Pill Icon Textbox" means **remove the text, keep the badge** —

The client's two clauses have to be read together:

> *"Remove Pill Icon Textbox: "15yrs of experience""* + *"Left side to display only
> the 2 side by side images."*

**"Left side"** is the About band's left column — the two photographs. So the
instruction is: on the left column, **only the two images should remain** — the
badge's pill-shaped textbox comes off it.

What actually exists today, measured:

```
src/marketing/pages/HomePage.tsx:461   <div class="years-badge rounded-[18px] bg-white shadow-lift max-md:hidden">
src/marketing/pages/HomePage.tsx:466     <strong class="years-badge-num …">15</strong>
src/marketing/pages/HomePage.tsx:467     <span class="years-badge-label text-ink">Years of Experience</span>
```

⚠️ **Two mismatches with the client's description, both worth recording.**

1. **The text does not say "15yrs of experience".** It renders as **`15` over
   `Years of Experience`** — two lines, no "yrs", no "of". The client is
   describing the badge from memory.
2. **It is not a "pill" any more.** The radius was changed from the template's
   `104px` lozenge to `rounded-[18px]` in round 3 — *"a horizontal icon BOX is a
   corner"* (`HomePage.tsx:458–460`). So "Pill Icon Textbox" names the shape it
   used to have.

**Decision: remove the badge from the About band's left column**, satisfying
*"only the 2 side by side images"* literally.

**This is the round's one genuinely ambiguous item, and it is not being guessed
at.** Three readings exist and they produce three different pages:

| reading | what happens | evidence for |
|---|---|---|
| **(a) Remove the badge** | the two photos stand alone; `15 / Years of Experience` disappears from the site | *"Left side to display only the 2 side by side images"* — the strongest clause; nothing else is on that column |
| (b) Remove only the **text** | a white rounded box with a blue disc and nothing in it | the word *"Textbox"*; but leaves an obviously broken element |
| (c) Remove only the **icon disc** | `15 / Years of Experience` stays, disc goes | *"Pill **Icon**"*; but contradicts "only the 2 images" |

**Recommendation: (a)**, and the task carries a **blocking question** rather than
an assumption. The factual loss under (a) is small and already covered: the Home
hero badge is the only place `15` appears, but *"since 2012"* is stated in the
footer licence line, the About paragraph and the `#choose` band, so no claim about
the company's age leaves the site. See §9 Q2.

⚠️ **Do not do (b) or (c) silently.** A half-removed badge is the shape of defect
that ships and reads as a rendering bug.

### 3.4 "All capitals" is a **content** change, not a CSS transform

Both service hero eyebrows are currently **sentence case in the HTML**, and the
class carries no `text-transform`:

```
src/index.css:1090   .hero-eyebrow { … font-weight: 700; letter-spacing: 0.6px; … }   ← no text-transform
src/marketing/pages/ResidentialPage.tsx:199   <span class="hero-eyebrow">Residential &amp; home services</span>
src/marketing/pages/CommercialPage.tsx:208    <span class="hero-eyebrow">Commercial &amp; facility services</span>
```

**Decision: change the string in the markup to `RESIDENTIAL & HOME SERVICES` /
`COMMERCIAL & FACILITY SERVICES`; do not add `text-transform: uppercase`.**

**Alternatives rejected:**

- *Add `text-transform: uppercase` to `.hero-eyebrow`.* Rejected for a reason this
  repo has already been bitten by (`src/index.css:1065`, the `.eyebrow` block):
  a transform **uppercases every string the class ever renders**, including any
  future reuse, and it leaves the DOM's text lowercase — so the rendered page and
  the accessibility tree disagree, and `renderToStaticMarkup` (which sees no CSS)
  cannot assert the change at all. The suite would be blind to it.
- *Use `uppercase` as a Tailwind utility on the two spans.* Same accessibility and
  testability objection, narrower blast radius. Still rejected: the suite asserts
  rendered text, and a CSS-only change is unassertable from the suite.

Editing the string is the only option the suite can verify, and it is the only one
that makes the DOM say what the page says.

### 3.5 "Bigger, with the number breaking under it" is **two** changes, and the

The client asks twice for the same treatment — once for residential, once for
commercial — so it is **one task, F9**, applied to both:

> *""CALL FOR A CONSULTATION" should be bigger and the number should linebreak
> under it."*

Today it is a single inline line at a small size:

```
src/marketing/pages/ResidentialPage.tsx:212
  <a href="tel:+15126084999" class="mt-7 inline-block text-[12.5px] font-bold uppercase tracking-[0.16em] text-white/80">Call for a Consultation: (512) 608-4999</a>
src/marketing/pages/CommercialPage.tsx:220   ← same string
```

**Two things are being asked for, and they are separable:**

1. **Bigger** — `12.5px` is clearly the "small print" size and is the only reading
   of "bigger" that is not a guess. The hero's own scale ladder is
   `h1 clamp(38px,4.6vw,64px)` → eyebrow `22px` → body `17px`; a step to
   **`clamp(18px, 1.4vw, 22px)`** puts it level with the eyebrow without competing
   with the h1.
2. **The number breaking under the label** — today the label and the number are
   **one text node**, so no break is possible. The number must become its own
   line: `CALL FOR A CONSULTATION` / `(512) 608-4999`.

⚠️ **The `tel:` link must survive the split.** The anchor currently wraps both, and
the whole thing is the click target. Making the number a `<br>`-separated second
line inside the same `<a>` keeps one tap target; splitting into two elements
creates two.

⚠️ **`uppercase` is already on this class** (`text-[12.5px] … uppercase`), which is
why the client sees `CALL FOR A CONSULTATION` in caps while the HTML says
`Call for a Consultation`. **That is the §3.4 defect in a second, already-shipped
place** — the DOM and the page disagree. F9's task should make the markup match the
visible text while it is in there, so the suite can assert it.

**A scale threshold applies here and it is not decoration.** "Bigger" at 1920 is
safe; at 390 a `22px` two-line CTA competes with the h1. The `clamp()` above
handles it, and the task's exit criterion says to check it at 390 — the width the
round-3 plan used as its mobile case.

### 3.7 The About paragraph is **three** separate instructions, not one rewrite

Item D packs three changes into one block. They are one task (F4) because they
touch one paragraph, but the task lists all three, because two of them are
**structural** and would be lost in a copy-only edit:

> *"make 2 lines and update text: "Call Indigo is your single phone call for any
> address." (Line Break) "Serving homes and facilities since 2012; We are
> Licensed, insured, and headquartered in Austin, Texas.""*

Current, verified as **one sentence with a mid-sentence em dash** and no break:

```
src/marketing/pages/HomePage.tsx:475
  Call Indigo is your single phone call for any address. Licensed, insured, and headquartered in Austin, Texas since 2012 — serving homes and facilities across Hays, Travis, and Williamson counties.
```

Three changes:

1. **"make 2 lines"** — insert a hard `<br>` after *"any address."*
2. **Rewrite sentence 1** — it is already identical to the brief, so this is a
   no-op that must be **confirmed** rather than re-typed.
3. **Rewrite sentence 2** — the facts are **reordered and re-punctuated**, not
   changed:
   - *"since 2012"* moves from the end of the Austin clause to the front of the
     service clause;
   - the em dash `—` becomes a semicolon `;` and a new sentence;
   - `We` is capitalised mid-string;
   - *"across Hays, Travis, and Williamson counties"* is **dropped** in the brief.

⚠️ **That last one is a factual deletion and it is not being made quietly.** The
county list names the **service area**, and it appears in the Round-3 plan's
list of facts a rewrite *must not break* (`plan-client-feedback-2026-09-26.md`
§Q3 lists Austin HQ and the service area among the things the footer and About band
both state). It **survives** in the residential hero chip's sibling copy
(`ResidentialPage.tsx:218`: *"Serving Hays, Travis, and Williamson counties"*), so
the site does not go silent about its area — but the **Home page** would. Flagged
as §9 Q4; **ship the brief's text if the client confirms**, because the client
supplied it in quotes.

⚠️ **A `<br>` inside this paragraph has a responsive side-effect.** At ≤1440 and
below, the *hero* paragraph's `<br>` is suppressed by
`.banner-lead br { display: none }` (`src/index.css:1034`), but this About
paragraph has **no such rule** — so the break is hard at every width including 390,
where the line will be positioned by the break rather than by the column. The task
says to check it at 390.

## 6. Sequencing, dependencies, critical path

**Almost nothing here is serialised.** The pages are independent files, and the only
true ordering constraints are:

```
F1 ─┬─ (all four footer copies + Contact, ONE commit — a partial edit is the defect)
F16 ┘
F3 ── F4          (same paragraph block in HomePage.tsx — edit sequentially, never in parallel)
F6 ── F17         (same SECTION on two different pages; independent, but the same
                   heading string appears on both — grep before and after)
F15 ── F14        (F14 creates the eyebrow that sits ABOVE F15's heading)
F8 ── F12         (the same edit shape on two pages — do both, or the heroes disagree)
```

**Critical path:** `F1 → F9 → suite`. F1 is four files plus a generated one. F9 is
the only task with a CSS scale decision and a mobile threshold. Everything else is
a string replacement.

⚠️ **`src/marketing/chrome-markup.ts` is GENERATED.** It carries a
"DO NOT EDIT BY HAND" header and is produced by `scripts/_brand.py`. F1 must change
**the generator**, then re-run it — otherwise the next regeneration silently
reverts the licence line and a test that reads the output will not catch it,
because the output was correct when it was written.

**Which tasks are genuinely parallel:** F2–F18 are all independent **files**, so
they can be written in any order — but they are **not** independent *edits*: F3 and
F4 are in the same file, as are F6/F7 and F13/F14/F15/F17/F18. **Edit one file
sequentially. Never batch parallel edits to the same file** — the writes race and
every call still reports success.

## 10. Release mechanics

Restated, because this is the part that gets skipped.

1. **Branch** — `release/v2.0.2` off `main` at `21304ed`. `main` **is branch-
   protected**: 1 approving review + the strict `Gates` check.
2. **Commits** — grouped per §4.2. Each `fix(…)` is followed by a
   `docs(changelog)` commit citing its own SHA. Commit messages go to
   `.git/COMMIT_MSG.txt` and are applied with `git commit -F` — heredocs mangle
   `\[` and `${}`.
3. **Gates** — `npm test` is **build + suite**. `test:only` does **not** rebuild.
   Run `npm test` as **one command**; two concurrent runs race on `dist/`.
4. **Version strings** — `package.json` and `README.md` move to `2.0.2` **in the
   release commit**, not before. v2.0.1 shipped with `package.json` reading
   `2.0.0-rc1` after `2.0.0` had gone out (`CHANGELOG.md:53–54`); the fix is to
   change them at the same moment as the tag.
5. **Tag** — `v2.0.2` on the **merge commit**. Do this after the merge, never on a
   feature commit.
6. **Merge** — `gh pr merge --squash --admin` with the owner's authorisation.
   `--auto` is refused by this repository (*"Auto merge is not allowed"*), and
   `gh pr review --approve` **cannot self-approve** the author's own PR.
7. **Deploy** — Vercel deploys on the merge. Confirm by **polling the JS chunk**,
   not the HTML shell — the shell is cached and reads green while the bundle is
   old. **An empty `statuses[]` is not evidence a deploy did not run.**
8. **Deployment log / changelog** — written **after** the fact, with the real SHAs.
9. **Wiki** — if a document is added, re-sync (`scripts/_wiki_sync.cjs`) and
   **never trust a page count written down in a doc**.
